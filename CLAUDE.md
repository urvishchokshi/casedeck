# CaseDeck

## Project

CaseDeck (formerly Casedeck/CasePrep) — case interview prep platform for ISB students. Case library with filters, progress tracking, partner matching, casebook downloads, frameworks. Content is extracted from IIM casebook PDFs via a manual Claude-assisted pipeline (scripts split PDFs and render images; extraction JSON is produced in claude.ai chats and bulk-imported). ~200-300 users, ISB-only via Microsoft login with @isb.edu enforcement.

## Stack

- Next.js (App Router, TypeScript, `src/` dir)
- Tailwind CSS
- Supabase (Postgres, Auth, Storage)
- Vercel for deployment
- No component libraries — UI primitives are built in-house

## Conventions

- All colors/radii/shadows come from CSS variables in `src/app/globals.css` — **NEVER hardcode hex values in components**. Consume tokens via Tailwind arbitrary values, e.g. `bg-[var(--card)]`. Font sizes are px literals matching the design (e.g. `text-[13.5px]`).
- Shared UI primitives live in `src/components/ui/` (Button, ButtonLink, Pill, Skeleton); other shared components in `src/components/` (AppShell, Brand, PageTitle, OutcomePill, RatingPill, ImageCard, ComingSoon).
- Everything strictly typed. No `any`.
- Server components by default; add `"use client"` only where interactivity requires it.

## Auth

Microsoft (Azure) OAuth via Supabase Auth, restricted to `@isb.edu` accounts.

- **Flow**: `/login` → `SignInButton` (browser client, `signInWithOAuth({ provider: 'azure' })`, redirectTo `/auth/callback` off `window.location.origin`) → `src/app/auth/callback/route.ts` exchanges the code for a session → redirect to `/cases`.
- **Origin rule**: all origin resolution lives in `src/lib/site-url.ts` (`import "server-only"`), which exports **two** functions because redirects and metadata want different things:
  - `requestOrigin(request)` → the host the browser is actually talking to: `x-forwarded-host` (+ `x-forwarded-proto`) → the request's own origin → null. Never reads config. **`src/proxy.ts` uses this** — a redirect to a *configured* host could differ from the host the browser is on and strand the session cookies the proxy copies onto the redirect.
  - `siteOrigin(request?)` → same, plus config fallback: forwarded host → the request's own origin *unless* it's loopback while deployed (`NODE_ENV !== "development"`), i.e. the internal address behind a proxy that didn't forward → `NEXT_PUBLIC_SITE_URL` (no trailing slash) → `VERCEL_URL` → the request origin anyway → `http://localhost:3000`. Used by the **auth callback** and, argless, by `metadataBase` (argless starts at `NEXT_PUBLIC_SITE_URL`, so metadata stays canonical).
  - ⚠️ Forwarded headers rank **above** `NEXT_PUBLIC_SITE_URL` on purpose: behind Vercel's proxy `new URL(request.url).origin` can be the internal `http://localhost:3000` — the cause of the "login lands on localhost" bug — and honouring the host the user actually reached keeps cookies and redirect on one origin. Consequence: someone arriving on a non-canonical alias (raw `*.vercel.app`, a preview domain) completes auth and **stays there** rather than being pulled to the canonical origin. Intended — it's the same PKCE reasoning as `SignInButton`.
  - `VERCEL_URL` sits above the request-origin fallback because it's a **runtime** var, unlike build-time-inlined `NEXT_PUBLIC_*`.
  - **Header trust**: Vercel overwrites `x-forwarded-*`, so they can't be spoofed there; browsers never send them, so an attacker can only forge them on their own request (no victim-driven path), and neither the proxy nor the cookie-reading callback is CDN-cacheable (no cache-poisoning amplification). Behind an *appending* proxy the rightmost value is the trustworthy one, so `trustedHeaderValue` takes that end — never the leftmost, which is client-supplied.
  - **`origin === "null"` trap**: `new URL("foo://host").origin` is the *string* `"null"` — truthy, and poison for every downstream `new URL(path, base)` (throws → 500). `toHttpOrigin` rejects non-`http(s)` protocols and that literal, so every source is filtered, not merely try/caught.
  - Two server-side `console.warn`s surface misconfiguration: one when `NEXT_PUBLIC_SITE_URL` is missing from a Vercel build, one when resolution falls all the way through to the request origin.
- **Sign-in `redirectTo`** (`SignInButton.tsx`) stays `${window.location.origin}/auth/callback` — deliberately the current browser origin, never `NEXT_PUBLIC_SITE_URL`: the PKCE code verifier is stored on that origin, so returning to a different host breaks `exchangeCodeForSession`.
- **Callback hardening** (Phase 6.1): whole handler wrapped in try/catch → `/login?error=auth` (never a raw 500); provider `error_description` logs truncated to 200 chars; if `SUPABASE_SERVICE_ROLE_KEY` is unset the non-ISB deletion is skipped with a logged warning instead of throwing — ⚠️ that's an enforcement gap, not just lost cleanup (the proxy only guards the Next app; an undeleted auth user can hit the Supabase API directly with the anon key), so the key is required in production.
- **Two-layer @isb.edu enforcement, server-side only** (`isIsbEmail` in `src/lib/auth.ts`):
  1. Callback: non-ISB email → the auth user is deleted via the service-role admin client (`src/lib/supabase/admin.ts`, guarded by `import "server-only"` — never import it into client code), session dropped, redirect `/login?error=domain`.
  2. Proxy: every request re-validates with `getUser()` (never `getSession`); a session with a non-ISB email is signed out and bounced. `(app)/layout.tsx` repeats both checks as belt-and-braces.
  - ⚠️ The Azure provider is **multi-tenant**, so the gate rests on the Azure `email` claim; a hostile tenant could self-assert an @isb.edu email. The real fix (NOT yet applied — dashboard config, no code): set the Azure Tenant URL in Supabase's Azure provider settings to ISB's tenant (`login.microsoftonline.com/a4dae443-38ab-404a-b331-9d1d337fcf37`); the registration itself must STAY multi-tenant because it lives outside ISB's directory. Full steps + caveats in README's deploy checklist. The email check remains as defense-in-depth either way.
- **Service-role key rule**: `SUPABASE_SERVICE_ROLE_KEY` is read ONLY by `scripts/pipeline/*.mts` and `src/lib/supabase/admin.ts` (the sanctioned, `server-only`-guarded exception above). Nothing else under `src/` may touch it.
- **Route protection**: `src/proxy.ts` (Next 16 renamed middleware → proxy). Runs on everything except `_next` assets and dotted files; refreshes the session per the @supabase/ssr cookie pattern (cookies are copied onto redirect responses). Unauthenticated → `/login`; authenticated visiting `/login` → `/cases`. `getUser()` is wrapped in try/catch and **fails closed** — an auth-server outage yields login redirects, not 500s.
- **Adding a public route**: add its path to `PUBLIC_PATHS` in `src/proxy.ts` (exact or prefix match). Current entries: `/login`, `/auth/callback`, `/api/health`.
- `/login?error=domain|auth` drives the error banner on the login page.

## Database

Schema lives in `supabase/migrations/` (`0001_init.sql` base, `0002_pipeline_tags.sql` pipeline tag columns, `0003_company.sql` consulting-firm attribution, `0004_library.sql` frameworks/materials + library-files bucket, `0005_outcome.sql` 3-way outcome enum replacing `completed`, `0006_remove_retry_marked.sql` drops the retry outcome (enum rebuilt as 2-way) + `marked_for_later`; applied manually in the Supabase SQL editor). TypeScript mirrors in `src/lib/types.ts`; clients in `src/lib/supabase/` (`client.ts` browser, `server.ts` cookie-based SSR).

- `profiles` — one row per user, auto-created by a trigger on `auth.users` insert; `is_admin` is protected by column-level grants (users can only update `full_name`/`campus`)
- `casebooks` — one per IIM casebook (`slug` unique; `pdf_url` holds the PDF's **storage path** in the `library-files` bucket — a path, NOT a URL; null = no PDF yet, set by `npm run upload-book`)
- `cases` — case content: `prompt`, transcript jsonb (`[{speaker: "interviewer"|"candidate", text}]` turns), solution/exhibit image columns (hold **storage paths**, not URLs), dynamic tags (`case_types`/`extra_tags` `text[]` with GIN indexes, `tags_inferred`), nullable `industry`/`difficulty`/`company` (consulting-firm attribution, verbatim, indexed), `source_start_page` + `printed_pages`, rating aggregates (`avg_rating`, `rating_count` maintained by trigger). **Idempotency key: `UNIQUE (casebook_id, source_start_page)`** — re-imports overwrite in place
- `user_case_progress` — per-user per-case: `outcome case_outcome` nullable ('done' | 'revisit'; null = not logged — both are an attempt), self_score (1–10), quality_rating (1–5), `completed_at` = when the outcome was last set; `UNIQUE (user_id, case_id)`. The `recompute_case_rating` trigger counts only rows with non-null outcome (and quality_rating)
- `match_profiles` — partner-matching profile, one row per user (PK = user_id)
- `frameworks` — framework/theory pages: **globally** `UNIQUE (title)` (the import-frameworks upsert key — cross-book title collisions overwrite), nullable `description`, nullable `casebook_id` (on delete **set null** → entry regroups under "General"), `image_paths` jsonb (ordered **storage paths in `case-images`** — same objects the case importer renders), `sort_order`. Select-only RLS; writes service-role only (import script)
- `materials` — standalone study-material downloads: `title`, nullable `description`, `file_path` (storage path in `library-files`), `sort_order`. Select-only RLS; rows added manually via Studio (no script)
- Enums: `difficulty_level`, `case_outcome`, `partner_status`, `mode_pref`, `campus_type`
- RLS enabled on all tables: users read shared content and write only their own rows; casebooks/cases/frameworks/materials/storage writes are service-role only (import pipeline / Studio)
- Storage: **private** buckets `case-images` (case + framework page renders) and `library-files` (casebook PDFs + study-material files) — authenticated read, service-role writes. Serve via signed URLs.

## Database rules

- Schema changes ONLY via new numbered files in `supabase/migrations/` — never edit an already-applied migration.
- The user applies migrations manually in the Supabase SQL editor. After writing a migration, always tell them to run it.

## Case library filters

/cases filter/search architecture (Phase 2.2; filter UI reworked to dropdown + pills):

- **URL search params are the single source of truth** (`?type=A&type=B&difficulty=Easy&industry=…&company=…&casebook=<slug>&rating=4&status=done&q=…`) — views are shareable/bookmarkable and back/forward work. Parsing/serializing/counting lives in `src/lib/case-filters.ts` (`parseCaseFilters` validates `difficulty` against the enum, `rating` ∈ {3,4}, `status` ∈ {done,not_done,revisit}; text params pass through — unknown values just match nothing; retired values like `status=retry|marked` or the old `marked=1` param are dropped, so stale URLs degrade to All).
- **Semantics**: multi-select within a group = OR (`case_types` via array overlap); across groups = AND. Rating is single-select (`gte avg_rating`). Status is single-select: done/revisit match `outcome` exactly ("Done" ≠ "any outcome"), not_done = null outcome (missing progress row included). Search `q` = case-insensitive `ilike` on title OR company, sanitized by **stripping** PostgREST/LIKE metacharacters (`sanitizeSearchQuery`) before interpolation into `.or()`.
- **Server side** (`src/app/(app)/cases/page.tsx`, server component): one filtered Supabase query (`overlaps` for type, `.in` for difficulty/industry/company, `casebooks!inner` embed + `.in("casebook.slug", …)` for casebook — lossless since `casebook_id` is NOT NULL) + an unfiltered facet query deriving distinct chip options + a `casebooks` list + the current user's `user_case_progress` rows, all in one `Promise.all`. Status filtering happens in JS **after** the query ("not started" = absence of a progress row, inexpressible in the SQL filter; fine under the 500 cap). Chip options are unioned with selected-but-unknown values so stale URLs render removable chips. Query capped at `.limit(500)` — pagination is a future enhancement if needed.
- **Row display** (`src/app/(app)/cases/CaseTable.tsx`, client): the server page maps query rows to display-ready `CaseTableRow`s. Desktop (`desk:`) = CSS-grid rows (no `<table>`), columns Case / Company / Industry / Type / Difficulty / Rating / Status — no Casebook column: the shortened book name (`shortBookName`: drop " Casebook", `IIM ` → `IIM-`) is the subline under the title. Difficulty renders as a 34px bar (Easy 33% / Medium 66% / Hard 100%) + label; Rating is plain muted text (value or "New"); Status is an `OutcomePill` or `—`. Below `desk:`: stacked card-rows with muted label prefixes. **Client-side load-more**: 20 rows per chunk, footer `Showing 1–N of M` + Load more; the component is keyed on `buildCasesSearchString(filters)` so the window resets when filters change. The source page number (`p. N`) is shown **only** on `/cases/[id]`; `source_start_page` is still selected as the order tiebreaker.
- **First-visit tour** (`src/app/(app)/cases/CaseTour.tsx`, client, mounted by the /cases page): 4-step spotlight walkthrough from the design — sidebar nav → status segments → filter dropdowns → case rows — targeting `data-tour` anchors (`nav` on the sidebar `NavLinks` / `nav-mobile` fallback on the Brand+hamburger row in `AppShell.tsx`; `status`/`filters`/`rows` in `CaseFilters.tsx`). Spotlight = fixed div whose 9999px `box-shadow` (`.cd-spotlight`, `--tour-dim`/`--tour-ring`/`--r-spot` tokens) dims everything else; spotlight + 300px step card glide between targets via `.cd-tour-move` (320ms). Card: STEP N OF 4 / title / body (step 3 interpolates the live case total) / dots / Skip / Next→"Got it", placed below-else-above-else-beside with 16px viewport clamps, `--sh-tour-card` shadow. Rendered through a `createPortal` to body (escapes the `.cd-fade-up` transformed ancestor), re-measures on resize + capture-phase scroll, Esc/backdrop-click skip. Runs once per browser after a 650ms delay — localStorage `cd-tour-v1`; remove the key to replay. When the "How CaseDeck works" guide is also unseen the tour waits for the guide's `cd-guide-done` event before starting its delay (guide first, tour second — see the Design section's Onboarding guide bullet).
- **Client side** (`src/app/(app)/cases/CaseFilters.tsx`, one `CaseFilterBar` component that also owns the results card): a centered segmented status control All|Not done|Revisit|Done on its own white track (single-select over `status`, All clears it), then the white results card whose header holds the centered `N results` headline, the debounced (300ms) search input, one dropdown trigger per dimension (Type, Industry, Difficulty, Company, Casebook, Rating — 32px `--shell` chips, accent-tint + count badge when active), and (when ≥1 active) per-value remove pills + "Clear all"; the server-rendered results (`CaseTable` or empty states) are slotted in as `children`. Popovers: anchored below-left (z-30, `--sh-modal`), in-flow full-width under `desk:` (`max-desk:contents` wrapper trick); >8-option dimensions get an autofocused client-side option search; multi-select applies immediately with selected-first order snapshotted at open; Rating is single-select and closes on pick; close on outside pointerdown/Esc/same-trigger, arrow-key roving focus, Esc restores trigger focus. All mutations go through one `push()` helper that flushes the pending debounced `q` into the same `router.replace(…, { scroll: false })` — no debounce races. Filter state still arrives as props from the server (no `useSearchParams`, so no Suspense boundary needed); the Rating dropdown always renders even while all ratings are null.

## Tracking

Per-user progress on cases (Phase 3.1; 2-way outcome since migration 0006). Table `user_case_progress` (see Database); **no delete policy**, so every undo is an UPDATE/upsert, never a delete. Both outcomes (done/revisit) mean "attempted", so both scores are required for every log.

- **Server actions** (`src/app/actions/progress.ts`, `"use server"` — the only mutation path): `logCase(caseId, outcome 'done'|'revisit', qualityRating 1–5, selfScore 1–10)` (outcome validated against an `as const` array, both scores required, validated server-side; sets `completed_at`), `clearOutcome` (outcome, scores + completed_at null). Both derive the user from the session cookie client (never `admin.ts`), upsert on `onConflict: "user_id,case_id"` with payloads that omit untouched columns (upsert only updates provided columns), return `{ ok } | { ok: false, error }` instead of throwing, and `revalidatePath("/cases")` + `revalidatePath("/cases/<id>")`. Writing/nulling `quality_rating`/`outcome` is what fires the `recompute_case_rating` trigger (security definer; averages non-null ratings over rows with non-null outcome).
- **Case detail** (`/cases/[id]` → `CaseActions.tsx`, client): top-right buttons per the design — **Mark done** (solid accent + dot; when outcome=done it becomes a green done-style button and clicking it unmarks via `clearOutcome`), **Mark revisit** (outline; orange fill when active, clicking unmarks), **Edit** (outline, only when logged, reopens pre-filled). The Mark buttons open the hand-rolled log dialog **preselected** to that outcome — Outcome segmented control (accent-tint selected) above 5 cumulative-★ quality buttons (orange-selected) and 10 square self-score buttons (accent-selected); save disabled until both scores chosen, Escape/backdrop close, no note field. Dialog backdrop/shadow tokens: `--overlay`, `--sh-modal`.
- **Outcome pill mapping** (`OUTCOME_META` in `src/lib/outcome.ts` + `src/components/OutcomePill.tsx`, shared by library table + mobile rows): Done = green dot-pill (`done` tone), Revisit = orange dot-pill (`revisit` tone).
- **Library**: Status column — `OutcomePill`, else "—" — from the per-user outcome map join; same pill on the stacked mobile rows.
- **Rating display rule**: show the average only once `rating_count >= MIN_RATINGS_TO_SHOW` (3), else "New" — everywhere, via `shownRating` in `src/lib/rating.ts` / `src/components/RatingPill.tsx`.

## Dashboard

/dashboard (Phase 3.2): read-only personal analytics — no writes, no new tables; server component only. Two queries in `Promise.all`: the user's `user_case_progress` rows with a `case:cases(…)` embed, plus a facet query over all cases; all aggregation happens in TypeScript in `src/lib/dashboard.ts` (pure functions, React-free).

- **Scoring rule** (uniform): "attempted" = any non-null `outcome` (done and revisit both count); a row contributes to averages only when `outcome !== null && self_score !== null`. Multi-type cases count once toward **each** of their `case_types` (Set-deduped per case). The attempted stat card carries a muted "N revisit" caption (omitted when 0) deep-linking to `/cases?status=revisit`.
- **Untagged grouping**: null industry/difficulty group under the `UNTAGGED` label, always sorted/shown last. The By-difficulty strip appends an Untagged segment only when null-difficulty cases exist.
- **Weakest ground**: ≤3 lowest-avg groupings across type + industry dimensions; a grouping needs **≥2 scored attempted cases** (`WEAKEST_MIN_CASES`) to qualify; card skipped entirely when nothing qualifies. ## Pipeline

Content extraction pipeline (`pipeline/` + `scripts/pipeline/`). Full workflow doc: `pipeline/README.md`. Scripts run via tsx, outside the Next build. **Note:** pipeline scripts are `.mts` — the `mupdf` package is ESM-only (top-level await) and the repo has no `"type": "module"`, so `.ts` scripts would be compiled as CJS and fail to import it.

- **Folder layout**: `pipeline/books.json` (registry `[{ slug, name, college }]`), `plans/` (per-case page plans), `prompts/` (claude.ai prompts), `frameworks/` (per-book framework entries + README), all versioned; `source/` (`<slug>.pdf` casebooks), `chunks/` (generated chunk PDFs + manifest), `inbox/` (extraction JSON from claude.ai chats), all gitignored.
- **Printed-page/offset convention**: all extraction output uses the page numbers **printed in slide footers**. Each plan/manifest carries `printed_page_offset` satisfying `pdf_page = printed_page + printed_page_offset`; the import script will use it to render solution screenshots from the source PDF.
- **Plan schema** (`plans/<slug>.json`, produced by the `prompts/split-plan.md` chat): `{ printed_page_offset, cases: [{ index, title, start, end }] }` — `start`/`end` are 1-based PDF pages, inclusive. Overlapping ranges are errors; gaps are warnings (divider pages).
- **Manifest schema** (`chunks/<slug>/manifest.json`): `{ slug, printed_page_offset, chunks: [{ file, start_page, end_page, case_indices, case_titles }] }`.
- **Dynamic-tag policy** (in `prompts/extraction.md`): tags come **verbatim from the book's slide header line** — never normalized to a predefined list. First header segment → `case_types` (split on "&"/"/"/"+"/"and" into an array), second → `industry`, difficulty word → nearest of Easy/Medium/Hard, rest → `extra_tags`. A segment (or case text) naming the consulting firm the case comes from → `company` (verbatim; judgment-based firm detection, no fixed list; null when unstated — never inferred; shown as a library column + detail pill, filterable via `?company=`). Missing header → fields are inferred (reusing labels seen elsewhere in the book) and flagged `tags_inferred: true` — but `company` is never inferred.
- **Chunk workflow**: register book in `books.json` + drop PDF in `source/` → claude.ai chat with `prompts/split-plan.md` + ToC pages produces `plans/<slug>.json` (chat asks for one calibration fact: the PDF page of the first case) → `npm run split -- --book <slug>` validates the plan and writes `chunks/<slug>/chunk-NN_pAAA-pBBB.pdf` (~8 cases each), `manifest.json`, and `_smoke-test.png` (chunk-01 page 1 at 2x, proving the mupdf render path) → per chunk: claude.ai Project (instructions = `prompts/extraction.md`), attach chunk, save JSON array to `inbox/<slug>/` → `npm run import -- --book <slug>`.
- **Import** (`scripts/pipeline/import.mts`, loads `.env.local` itself for the service-role key): zod-validates every inbox JSON array (code fences stripped; extraction `error` objects and invalid cases go to a skip report, never abort the run; duplicate first-printed-page across files → last wins), renders each needed solution/exhibit page from the **source** PDF at 2x via mupdf (once per unique page), uploads to the private `case-images` bucket at `<slug>/p<printed>.png` (`upsert: true`), and upserts `casebooks` (by slug) + `cases` on **`(casebook_id, source_start_page)`** — `source_start_page` = first printed page. The DB stores **storage paths** in `solution_image_urls`/`exhibit_image_urls`; mint signed URLs at read time. Re-runs are idempotent; inbox files can be kept or deleted.
- **Casebook PDF upload** (`scripts/pipeline/upload-book.mts`): uploads `source/<slug>.pdf` to `library-files/<slug>.pdf` (upsert) and sets `casebooks.pdf_url` to that storage path. The casebook row must already exist (`npm run import` first) — the script never creates it.
- **Tag cleanup** (`scripts/pipeline/tags.mts`, subcommands `export`/`apply`): manual, user-triggered merge of fragmented filter values ("E-Commerce"/"E-commerce", "McKinsey"/"McKinsey Buddy Case") — **never automatic during import**; the verbatim extraction policy stands. Workflow: `npm run tags-export` (paginated full-table scan → `pipeline/tags/current.json` + paste-ready console block + existing-mapping echo) → claude.ai chat with `prompts/tag-cleanup.md` → save the returned JSON to `pipeline/tags/mapping.json` → `npm run tags-apply -- --dry` (preview with per-entry row counts, writes nothing) → `npm run tags-apply`. Mapping shape: `{ industry|case_types|company: { "<from>": "<to>" | null } }` — null clears the field / removes the array element; scalars apply as `UPDATE … WHERE col = from`, `case_types` as read-modify-write by id (replace + order-preserving dedup). **`mapping.json` is cumulative and versioned in git** — each round feeds it back into the chat and saves the full old+new mapping so canonical choices stay stable; `current.json` is a gitignored regenerable snapshot. Apply is idempotent (re-runs report zeros), warns-not-fails on keys matching nothing, and rejects chained mappings (a target that is also a key in the same dimension).
- **Frameworks import** (`scripts/pipeline/import-frameworks.mts`, doc: `pipeline/frameworks/README.md`): reads `pipeline/frameworks/<slug>.json` — a hand-written (or claude.ai-produced) array of `{ title, description (nullable), printed_pages: number[], sort_order? }` using printed slide-footer page numbers + the plan's `printed_page_offset`. Renders each page at 2x, uploads to `case-images/<slug>/p<printed>.png` — **pages already rendered by the case import are reused by existence, not re-rendered** (delete the storage folder to force fresh renders after a PDF revision) — and upserts `frameworks` on `title`. Invalid entries → skip report; idempotent re-runs. Requires the casebook row to exist.
